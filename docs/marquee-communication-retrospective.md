# 跑马灯沟通复盘：沟通成本与投机式交付（2026-10-15）

> 技术根因、弯路清单、参数规则详见姊妹篇 `docs/marquee-fix-retrospective.md`（R1-R7）。
> 本文件聚焦用户点名的两个问题：**①为什么沟通成本这么高、用户该怎样表述 AI 才能理解；②跑马灯这么简单的需求为什么改了这么多轮还不对、还试图投机解决、如何避免。**

## 一、用户点名的两个问题

1. **为什么沟通成本这么高？** 用户该怎样表述，AI 才能真正理解。
2. **跑马灯这么简单的需求，为什么改了这么多次还是不对，还试图用投机的方式解决？如何避免。**

## 二、沟通成本高的根因（诚实复盘，来自实际多轮对话）

| # | 根因 | 具体表现 |
|---|---|---|
| 1 | **把现象当需求复述** | 用户描述"叠字/不动/空屏"（现象），AI 复述时自行翻译成实现语言（如把"无缝循环"翻译成"gap ≥ 视口宽"），投机偏离需求 |
| 2 | **把静态截图脑补成先后过程** | 用户发一张截图（某一时刻快照），AI 脑补成"先→后"的过程，得出与事实相反的结论 |
| 3 | **理解未对齐就动手** | 用户多次要求"你复述一下""复述""我怀疑你没有理解"——AI 在需求未确认时就开始改代码 |
| 4 | **用技术术语掩盖没听懂** | 用户问"跑马灯/两个毛玻璃组件"，AI 谈"basicMarquee 参数错位/slideInVertically"，鸡同鸭讲 |
| 5 | **数学/时序计算不透明、算错** | "两次动作时间"问题：AI 计算动画总时长时把第一个动作的动画时间弄丢，用户直接指正"你数学不好吧" |
| 6 | **不区分角色与组件** | 动画对象描述混乱（"三大件"一度被理解为遮罩/面板/动作条，实际是动作条上的三个组件）——没有固定名称体系 |

## 三、如何表述才能被理解（沟通规则 C1-C6）

- **C1 先复述、再动手**：用户描述需求后，AI 先用**用户的语言 + 固定组件名称**复述，用户确认后才改代码。禁止跳过复述直接实现。
- **C2 区分"现象"与"需求"**：用户说"叠字""不动"是**现象**；"无缝循环、两字符间距、不空屏"是**需求**。分开记录，AI 不得自行把现象翻译成实现方案。
- **C3 截图是快照，不是过程**：静态截图只代表某一时刻的画面。涉及动态行为时，问清楚先后/运动方向，不脑补成"先→后"。
- **C4 使用固定名称**：组件/模块固定命名（动作条、动作条三组件、封面按钮、播放详情面板、遮罩、主页列表、专辑列表页），AI 全程使用固定名称，不迁就模糊表述，帮助用户逐步掌握术语。
- **C5 数学与时序透明**：动画时长、位移、路程、总时长的计算**摆出来给用户看**（含每一步），用户能直接指出错误，不做黑箱计算。
- **C6 不把"理解"伪装成"完成"**：没听懂就直说、先对齐；不得在理解偏差的情况下交付"看似完成"的结果。

## 四、为什么改了这么多轮、如何避免投机（交付规则 S1-S5）

- **S1 禁止在现象层打补丁**：跑马灯改 8+ 轮的核心教训——反复调 dp/px、加大 gap 只是缓解症状，从未质疑"自研方案"本身（测量与渲染不一致的深层根因）。
- **S2 先查官方/业界标准实现**：自研方案有深层缺陷时，先查官方标准（basicMarquee）再决定，不自己造轮子反复修补。
- **S3 投机式交付会被拆穿且浪费时间**：用户对"gap ≥ 视口宽"这类绕过方案零容忍（当时直接拆穿）。任何"绕过实现"都必须说明取舍并获得同意。
- **S4 排查顺序固定**：先读自己的调用代码 → 对照官方文档/源码 → 排除环境 → 取证真机（详见技术复盘 R3）。禁止先验"官方没问题""环境没问题"。
- **S5 UI 动画验证只能真机**：Robolectric 的 captureToImage/waitForIdle 无法验证动画帧（对照实验证实）。动画类排查开始前先确认验证通道，不把轮次花在"证明测试方法可行"上。
